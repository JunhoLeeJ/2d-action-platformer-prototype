# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A 2D side-scrolling action platformer prototype, implemented as plain HTML/CSS/JS: `index.html` (markup + inline `<style>` + `<canvas>`) loading a sequence of classic `<script src>` files under `js/`. No build step, no bundler, no package manager, no dependencies, no test suite — deliberately kept this way so `index.html` still opens directly via `file://` with zero setup (see "File layout" below for why this rules out ES modules).

For *why* the game works the way it does and the exact behavior of every system, read `PRD.md` (product intent) and `SRS.md` (functional requirements with exact numbers) before making non-trivial gameplay changes — they document the current implementation, not aspirational features. Keep them in sync when you change behavior they describe.

This project is being built out into a larger story-driven game (multiple floors, each with several zones, cutscenes, an AI companion) beyond what PRD/SRS describe. **Before starting any zone/floor/story content work, read `ROADMAP.md`** — it holds the original narrative design spec broken into a checklist (what's done, what isn't, exact dialogue lines and numbers to preserve) plus a recommended next-work order. Update it whenever you finish a checklist item, change the recommended order, or add new reusable engine infrastructure while building content — it's the only continuity across sessions for "where were we," so treat it with the same discipline as PRD/SRS.

`LATER.md` is a separate, much lighter-weight document — a running "post-it" list of details deliberately skipped or half-done in service of moving fast toward a finished game (placeholder cutscenes, missing difficulty tuning, etc.), *not* a progress tracker like ROADMAP.md. Add a short entry there whenever you knowingly cut a corner the user will want to revisit later; check it off or delete it once actually addressed.

## Commands

- **Run locally**: open `index.html` directly in a browser, or `npx serve .` for a local server.
- **Deploy**: `vercel` (project is already linked via `.vercel/`; push to `master` does not auto-deploy — deployment is manual). There is no lint/build/test command; there is no CI.

## Architecture

### File layout

Read `js/main.js`'s top-of-file "게임 개요" comment block first — it's a map of how the core systems interlock. Files load as plain classic `<script src>` tags (no `type="module"`, no bundler — modules fail via CORS when `index.html` is opened with `file://`, which would break the zero-setup "just open it" workflow), so every file shares one global scope. Load order in `index.html` matters in exactly two places — everything else resolves at call time, not parse time:

```
js/config.js                    CONFIG
js/engine/dom.js                canvas/ctx/W/H, clamp/rectsOverlap/circleRectOverlap
js/engine/input.js               heldKeys/justPressed/pendingKeyAfterFreeze, event listeners
js/engine/timestop.js           timeStopTimer, triggerTimeStop
js/engine/camera.js             camera, updateCamera, cameraOverrideTarget (cutscene camera holds)
js/entities/enemies.js          적 팩토리(makeTurret/makeSniper/makeChaser)/AI, enemies[], projectiles[]
js/entities/player.js           player, ghostNpc, gameState, 표류(drift) 시스템, respawnPlayer
js/engine/zones.js              ZONES registry, currentZone, loadZone(), 존별 규칙 플래그(ruleFlags)
js/engine/checkpoint.js         currentCheckpoint, activateCheckpoint()
js/engine/cutscene.js           트리거 시퀀스 엔진(대화/카메라 홀드/애니메이션/페이드), 텍스트박스
js/engine/qapanel.js            QA 패널(구역 이동) - qaPanelOpen, warpToZone() (§ 아래)
js/rendering.js                 draw(), updateHud()
js/levels/*.js                  존 데이터 - ZONES에 등록. zones.js *다음*에 로드되어야 함 (파싱 시점에 등록하므로)
js/engine/mainmenu.js           메인 메뉴("게임 시작"/"구역 선택") - 진짜 부트스트랩 진입점 (§ 아래)
js/main.js                      update()/loop()/부트스트랩 - 반드시 맨 *마지막*에 로드
```

Every `js/levels/*.js` file wraps its content in an IIFE (`(function(){ ... })();`) rather than declaring top-level `const`/`let` — classic `<script>` tags share one lexical scope, so two zone files both declaring e.g. `const groundY` would throw a `SyntaxError` and take down the whole page. Follow that pattern for every new level file.

### World model: zones, floors, checkpoints, cutscenes

The world is a **graph of discrete zones** (`ZONES` in `js/engine/zones.js`), not one continuous world. Each zone is a self-contained level — its own `width`/`height`/platforms/gaps/wall-gates/enemy spawns/checkpoints/doors/trigger zones — and `loadZone(zoneId, spawnAt)` swaps `currentZone` (rebuilding `enemies` fresh from that zone's `enemySpawns` every time, never mutating in place, so no state leaks between zones) and repositions the player/ghost/camera. `floor` on a zone def is bookkeeping metadata only — there's no separate "floor transition" mechanism; a floor boundary is just an ordinary door into a zone that happens to carry an entry cutscene (see below).
- **Camera follows both axes** (`js/engine/camera.js`): `updateCamera` runs the same deadzone+exponential-lerp logic on X and Y independently (`CAMERA_DEADZONE_W`/`CAMERA_DEADZONE_H`), with **separate smoothing constants per axis** (`CAMERA_SMOOTHING_X`/`CAMERA_SMOOTHING_Y` — Y is tuned higher so falls don't visibly lag the camera; tune them independently rather than reintroducing one shared constant), clamped to `currentZone.cameraBounds` (`{minX,maxX,minY,maxY}`, derived from the zone's `width`/`height` in `loadZone`). Most zones set `height` equal to the canvas height `H` so `maxY` collapses to `0` and there's effectively no vertical scroll (matches the original game's fixed-height feel) — give a zone a `height` taller than `H` (see `f1z2_platforms` for a worked example: a climbing tower well above one screen height) when you actually want vertical traversal to pull the camera up/down. Don't set a zone's `width`/`height` *smaller* than `W`/`H` — the clamp range inverts (`maxX/maxY` goes negative) and collapses the camera to a fixed `0`, which silently breaks follow on that axis.
- **Keep `groundY + groundH` close to the zone's `height`** (small margin, ~20px — see any current zone file for the convention). The camera's bottom clamp shows everything up to `height`; if the ground sits far short of that, standing on the ground shows a chunk of empty void below it and the character reads as "floating." This bit everyone the first time `H` was raised without moving `groundY` down to match — don't repeat it when adding new zones or changing `H` again.
- **Vertically-tall zones should cap their top with a ceiling, mirroring the ground convention above**: a full-width `zone.floors` entry at `{y: 0, h: <bottom edge>, gaps: []}` (no `xMin`/`xMax` so it spans the whole zone, same as how the base ground does) — same reasoning as the `groundY+groundH` rule, just upside down: the camera's top clamp is `0`, so the ceiling's own top must sit exactly at `y:0` or a gap of empty void shows above it when the camera scrolls all the way up. Size the ceiling's headroom (distance from where the player normally stands up there to the ceiling's underside) so a **single** jump clears it but a **double** jump (timed at the apex of the first) bonks it — simulate the actual frame-stepped jump physics (gravity/clamp/position order copied from `updatePlayer`) rather than eyeballing the continuous `v²/2g` formula, since real double-jump height depends on retrigger timing (`f1z2_platforms`'s top-of-shaft ceiling is a worked example: single-jump rise ≈131px, double-jump-at-apex rise ≈275px, so a ~200px headroom clears one and blocks the other with margin on both sides).
- **Doors**: a zone's `doors.right` is real data (`{x,y,w,h,targetZoneId}`) that `loadZone` turns into a synthesized trigger — walking into it fades to black, swaps zones at full-black (`onMidpoint`), fades back in. The `onMidpoint` callback just calls `enterZone(door.targetZoneId)` (see the entry further down) — it must *not* do its own cutscene cleanup (e.g. nulling `activeSequence`), because `onMidpoint` runs synchronously from inside that very fade sequence's own `updateFade`/`updateSequence` call stack; killing `activeSequence` there crashes the very next line (`activeSequence.fadeElapsed` on a `null`). `doors.left` is background-only geometry with no trigger (no generic backward travel — a specific narrative exception, if one is ever needed, is a hand-authored trigger, not an engine feature). Every `doors.right` should also carry **`yMax`** and **`landingY`** — this is a standing requirement for *all* doors going forward, not just ones on an elevated platform (`f1z1_entry`'s plain ground-level door sets both too):
  - **`landingY`** (the y of the surface the door's platform/floor sits on — `groundY` for an ordinary ground-level door, the platform's own surface y for an elevated one) drives the airborne-entry beat: if the trigger fires while `!player.onGround`, the door plays a short scripted sequence instead of fading immediately — auto-walk right off the visible camera view, *then* the normal fade/zone-swap (the "fall to a natural landing" part of this beat is no longer door-specific — see `fireTrigger()` below, which now does it for every trigger). Only omit `landingY` if a door genuinely has no single well-defined floor to fall to (e.g. reachable from multiple different heights) — that falls back to the original instant fade, but treat that as the exception, not the default. This is what the `"custom"` cutscene event type and function-valued `trigger.sequence` (see below) exist for — reuse them for any future "can't just freeze-and-cut, needs a beat first" transition rather than inventing a parallel mechanism.
  - **`yMax`** (same asymmetric-scoping idea as trigger zones, see below) keeps the trigger from firing far below where the door visually sits — without it, walking along any lower ground under an elevated door's X column (or jumping high over *any* door's X range) fires it purely on X. Keep it tight against the associated floor's own standing height, not just "loose enough to exclude the ground": an early version of `f1z2_platforms`'s door used `yMax:900` reasoning only "must exclude the far-away ground" — but that left ~300px of open air *below* the platform where jumping around near the shaft (mixing double-jumps while falling) could still overlap the door's X range and incorrectly fire it from well below the platform, teleporting the player. The fix: derive `yMax` from `landingY - player.h + <~25px buffer>` (the exact Y the player has when properly standing there), not a round-number guess — see `f1z2_platforms` for the worked `standingTopY`/`landingStandingTopY` pattern.
  - **"Land naturally before any trigger's sequence starts" is now a generic engine behavior, not door-specific.** `fireTrigger()` (`js/engine/cutscene.js`) checks `player.onGround` itself, and if false, prepends a `{type:"custom", tick: makeFallUntilGroundedTick()}` event in front of *whatever* the trigger's own sequence is — applies uniformly to every `walkIn`/`auto` trigger in every zone (door or not), per explicit user request ("트리거존 나올 때마다... 점프를 자연스럽게 캔슬해주는 연출을 넣어달라"). `makeFallUntilGroundedTick()` (`js/engine/zones.js`) doesn't need a known `landingY` the way the door-specific `makeFallInPlaceTick` (now removed) did — it applies gravity each tick and calls **both** `resolveSolidVerticalCollisions()` *and* `resolveOneWayVerticalCollisions(prevBottom)` (both factored out in `js/entities/player.js` so `updatePlayer`'s own Y-axis block and this cutscene tick share identical collision logic), returning `true` once `onGround` naturally becomes true — so it lands correctly on solid ground *or* a one-way platform (e.g. `f1z2_platforms`'s shaft-top landing, which is a one-way platform — the door's own `makeFallInPlaceTick` never had to handle that case since it snapped straight to a known `landingY`, but the generic version does, since it's reused everywhere). Not resolving one-way platforms here was a real bug caught before shipping — `resolveSolidVerticalCollisions()` alone only checks `currentZone.solidPlatforms`, so a fall tick relying on it exclusively would fall straight through any one-way-platform landing zone. Since `vy` is never force-reset (gravity just keeps integrating from whatever it already was), a player still ascending when the trigger fires decelerates, peaks, and falls "naturally" rather than being cut off mid-jump — reuse this any time a new trigger needs to freeze the player without an ugly mid-air pop or a hard teleport (1층 구역 5's fatal encounter is a worked example: its custom "slow walk" event no longer needs to snap `player.y` itself, since this prefix already guarantees the player is grounded by the time it starts).
  - **Derive `entryPoint`/`checkpoint`/door `y` from `floorY - player.h` (or `floorY - door.h` for the door itself), never a rounded guess.** Every zone file computes a `standingTopY = groundY - player.h` (and `landingStandingTopY` for elevated platforms) once, then reuses it — this is what fixed two real bugs at once: doors whose `y+h` extended a few pixels past the floor's surface rendered visibly sunk into the ground/platform, and entry points a rounded amount above the true standing height made the player visibly free-fall for an instant on zone entry (including on first game boot). Keep using the derived constant, not a re-eyeballed number, when adding new zones.
- **Trigger zones** (`zone.triggerZones`, fired by `js/engine/cutscene.js`) come in two kinds: `"walkIn"` (fires once the player's **X range** overlaps `[xMin,xMax]` — deliberately no Y check by default, so it can't be jumped over) and `"auto"` (fires immediately when its zone loads). A `walkIn` trigger can optionally add `yMin`/`yMax` to scope itself to one floor of a multi-floor zone (so a trigger authored for a high floor doesn't also fire from a lower floor at the same X) — when you do, set them **asymmetrically**: `yMin` generous (reaches well above the intended floor, since approaching from above should still count) and `yMax` tight (barely below the floor's own surface, since a floor underneath shouldn't count). `repeatable: true` triggers require the player to fully leave and re-enter the zone before firing again — `scanTriggerZones` tracks per-trigger enter/exit state (`triggerContactState`) specifically so standing still inside a repeatable trigger after its sequence ends doesn't refire it every frame; don't reintroduce a pure level-check (`isInside` with no edge detection) or that bug comes back. Both kinds play an ordered `sequence` of events (`dialogue`/`cameraHold`/`animation`/`fade`/`callback`/`custom`) through `startSequence`/`advanceSequence`/`endSequence` — `endSequence` is the **one** exit point every sequence funnels through (camera override cleared, textbox hidden, next queued auto-trigger drained), which is what guarantees a sequence can never leave dangling UI state or let two sequences run concurrently. `custom({tick, onStart})` runs `tick(dt)` every frame until it returns `true`, for beats that wait on a runtime condition rather than a fixed duration (the door fall/walk-offscreen beat above is the worked example) — don't reach for a fixed-duration event and fudge the number when what you actually need is "until X happens." `trigger.sequence` can also be a **function** (`() => events[]`) instead of a static array — `fireTrigger` evaluates it at the moment the trigger actually fires, so it can branch on runtime state the zone-load-time array couldn't see (e.g. the door's grounded-vs-airborne branch above); give a plain array when there's nothing to branch on, same as before. **`zone.triggerZones` and `zone.ambientProps` can *also* each be a function** (`() => [...]`) instead of a static array — `loadZone()` evaluates them once per zone load (not once per frame), so a zone can hand back a different trigger/prop list depending on session state the zone-def-parse-time array couldn't see (e.g. `f1z5_fatal_encounter` swaps its fatal-approach trigger + reachingEntity/fragmentObject props for a drift-unlock trigger + a single `crackMark` prop once `hasSeenTrigger("f1z5_fatal_encounter","fatal_approach")` is true — see the 1층 구역 1 재진입 처리 zone files). `hasSeenTrigger(zoneId, triggerId)` (`js/engine/cutscene.js`) is the read-only lookup into `seenTriggerIds` meant for exactly this kind of check from level files. Give a plain array when there's nothing to branch on, same as before — this is purely additive, every existing zone's static arrays still work unchanged. A **door** (`zone.doors.right/left`) can't use this same trick, since the door object itself stays fixed in `currentZone.doors` for the whole time a zone is loaded (no "reload" happens on revisit-without-re-entering) — for a door-attached visual that depends on session state, give the door a `crackWhen: () => boolean` instead, which `drawDoor()` (`js/rendering.js`) checks fresh on every frame it's drawn rather than once at load (`f1z1_entry`'s right door is the worked example — a crack overlay that appears once the player has died in `f1z5_fatal_encounter`). `crackWhen` is purely a rendering hook; it never affects the door's own trigger geometry (`xMin`/`xMax`/`yMax`/`landingY`). While a sequence runs, `gameState === "cutscene"` routes around `updatePlayer()` entirely, which is also what makes enemies/projectiles/death auto-freeze during cutscenes (they already gated on `gameState !== "playing"` before cutscenes existed — extending the enum got that for free instead of adding new guards). Reuse this system for any new story beat rather than inventing a parallel "block input" flag.
- **Checkpoints**: `currentCheckpoint` (`js/engine/checkpoint.js`) is a mutable `{zoneId,x,y}`, set via `activateCheckpoint()`. `respawnPlayer()` composes `loadZone(currentCheckpoint.zoneId, currentCheckpoint)` (handles same-zone *and* cross-zone respawn uniformly) then calls `resetPlayerVitals()` (`js/entities/player.js`) to restore HP/attack/drift/velocity/`onGround` to fresh values. **`loadZone()` itself never touches vitals or the checkpoint** — by design, so death-vs-normal-transition can each decide independently whether to reset them — but *every* other "arrive in a zone for real" path does reset them via `resetPlayerVitals()`, per explicit user request that door transitions and warps always start at full HP with the checkpoint correctly re-pointed at the new zone (this used to not be true for doors — HP/cooldowns silently carried across, and the checkpoint stayed on the *previous* zone — both were reported as bugs and fixed by routing doors through `enterZone()`, below).
- **Checkpoint pillars**: starting with `f2z2_checkpoint` (the zone that narratively introduces the mechanic), **every zone's `doors.left` gets a `zone.ambientProps` entry of `{type:"checkpointPillar", x,y,w,h, checkpointId}`** by default — per explicit user request, this is now a standing convention to apply without being asked, the same way every zone already gets a `doors.right` trigger. Skip this only for zones that predate the mechanic's introduction (1층, and `f2z1_gyeol_encounter`) — don't retroactively add it there.
  - **The pillar must not light up (and must not become the respawn point) until the player physically touches it** — a door transition alone must never activate it, per explicit user correction to an earlier version of this feature that auto-lit every zone's pillar on entry. Concretely: every zone with a pillar sets **`checkpointRequiresTouch: true`** on the zone def, which makes `enterZone()` (`js/engine/zones.js`) skip its normal automatic `activateCheckpoint()` call for that zone — the pillar's own `walkIn` trigger is what actually calls it, on contact. The introducing zone (`f2z2_checkpoint`) plays a real cutscene the *first* time (cameraHold + `animation` hook), gated behind a closure-scoped `let introShown` flag local to that zone file (**not** `hasSeenTrigger`, which never records anything for `repeatable:true` triggers) — every zone after that (and every touch after the first, including revisits to the intro zone) just fires the `activateCheckpoint()` callback with no ceremony. **The trigger must be `repeatable:true`**, because re-touching an already-active pillar (or backtracking to an old one) should still work — the user was explicit that stepping on a checkpoint "whenever" should always re-apply it, not just once per zone visit.
  - **Give the pillar's `walkIn` trigger a generously-tall `yMin` and a tight `yMax`** — same asymmetric convention as multi-floor trigger zones elsewhere (yMin generous so a jump arc over the pillar still registers — per explicit user request that a checkpoint can never be skipped by jumping over it — yMax tight so it doesn't misfire from a different floor below in a future vertical zone). `f2z2_checkpoint`/`f2z3_legacy_arena` use `yMin: pillarY - 350` (clears even a double-jump apex) and `yMax: standingTopY + 25` (the standard door/trigger tight-below margin).
  - **The zone def's own `checkpoints[].active` must default to `false`**, not `true` — since `enterZone()` no longer calls `activateCheckpoint()` for these zones, nothing ever overwrites that static baked-in value until the player actually touches the pillar; leaving it `true` (copy-pasted from a non-touch zone) makes the pillar appear lit from the moment the zone loads, silently reintroducing the exact bug this whole mechanism exists to prevent. This bit us once already — always double-check this value when adding a new pillar zone.
  - **Exactly one checkpoint is ever lit at a time**: `activateCheckpoint()` (`js/engine/checkpoint.js`) loops over *every* registered zone's `checkpoints` array (not just the zone being activated) and sets `cp.active` accordingly, so activating a new one always clears every other zone's stale `active:true` — `drawCheckpointPillarProp` (`js/rendering.js`) reads that flag fresh every frame (`currentZone.checkpoints.find(cp => cp.id === prop.checkpointId).active`), the same "don't cache what can change mid-visit" reasoning as `door.crackWhen()`, rather than a `hasSeenTrigger()` check (which would leave multiple pillars lit forever once each was ever touched — wrong, since only the *current* respawn point should glow).
  - **`enterZone()`'s crash-safety fallback for a touch-required zone never lights anything**: if `currentCheckpoint` is still `null` the very first time such a zone is entered this session (e.g. a fresh boot warping straight into `f2z2_checkpoint` via the QA panel, before any checkpoint was ever set), `enterZone()` assigns `currentCheckpoint` directly (`{zoneId, x, y, checkpointId: null}`) instead of calling `activateCheckpoint()` — this keeps respawn safe (never `null`) without lighting a pillar the player hasn't touched, preserving the rule above even in this edge case.
- **Keep monster spawns well clear of a zone's checkpoint/entry point** — a monster within `CONFIG.ENEMY_DEFAULT_DETECTION_RANGE_W` (480px) of where the player actually stands after respawning will aggro the instant they respawn, before they can react. `f2z3_legacy_arena`'s `SPAWN_SAFE_OFFSET` constant is the worked example: rather than nudging individual enemy/platform coordinates, the whole level's content (enemies, platforms, gaps, the wall gate, the far wall, `width`) shifts right by one constant so the relative layout/pacing is untouched and only the gap between the checkpoint and the first threat grows. Apply this to every new zone's monster placement going forward, per explicit user request — leave a comfortable margin beyond the raw 480px (the worked example used ~640px) since detection uses center-to-center distance, not edge-to-edge.
- **`enterZone(zoneId)`** (`js/engine/zones.js`) is the shared core every "start fresh in a zone" path funnels through — `loadZone(zoneId, def.entryPoint)` + `activateCheckpoint(...)` + `resetPlayerVitals()`, in that order. Both the door trigger's `onMidpoint` and the QA panel's `warpToZone()` call this one function now, per explicit user request that the two paths behave *identically* — before this, `warpToZone()` duplicated its own copy of the checkpoint+vitals-reset logic inline, which is exactly how the two paths drifted out of sync in the first place. `enterZone()` deliberately does **not** touch cutscene/timestop state (`activeSequence`, `endFade()`, etc.) — see the Doors bullet above for why that would crash the door's own in-progress fade sequence; `warpToZone()` does that cleanup itself *before* calling `enterZone()`, since a warp (unlike a door's `onMidpoint`) can be triggered from any arbitrary moment, including mid-cutscene. `respawnPlayer()` deliberately does **not** use `enterZone()` — respawning returns to `currentCheckpoint`, which is not guaranteed to equal the zone's `entryPoint` (a zone can have checkpoints elsewhere), so it calls `loadZone`/`resetPlayerVitals()` directly instead.
- **Rule flags** (`zone.ruleFlags`, defaults in `RULE_FLAG_DEFAULTS`): per-zone overrides (`disableJump`/`disableAttack`/`disableDrift`/`playerInvincible`/`hpFloor`) for tutorial-style exceptions, read via `getRuleFlag(name)`. `driftUnlocked` is a separate single global boolean (not a rule flag) since drift is meant to be locked/unlocked once for the whole game by a specific story beat, not per zone. **`playerHpRegenDelay`/`enemyHpRegenDelay`** (read by `tickHpRegen(entity, dt, ruleFlagName)`, `js/entities/enemies.js`) are two independent flags, not one shared `hpRegenDelay` — they used to be a single flag covering both the player and every monster in the zone, but zone 4's mimeA needing "player recovers, monster does not" made that unworkable. Set both (to the same `CONFIG.HP_REGEN_DELAY`) when you want the old shared behavior (zone 3 does this), or just one when you don't.
- **Floors and walls are level-design primitives, not just the base ground**: `zone.floors` (`{y,h,gaps,xMin?,xMax?}[]`) and `zone.walls` (`{x,w,gaps,yMin?,yMax?}[]`) let you place additional full (or range-scoped) horizontal/vertical barriers anywhere, each optionally broken by `gaps` (openings) — `loadZone` expands them into rects via `buildHorizontalBarrierSegments`/`buildVerticalBarrierSegments` (the same helper that already builds the base ground from `groundGaps`) and merges them into `currentZone.solidPlatforms`. `xMin`/`xMax` (floors) and `yMin`/`yMax` (walls) default to the full zone width/height when omitted (matches the base ground's behavior) — set them to confine a floor/wall to a sub-region (a room, a shaft) instead of spanning the whole zone. `f1z2_platforms`'s climbing tower is a worked example of combining both: `walls` with `yMin`/`yMax` build a narrow contained shaft (visually and physically guides the player, rather than an open floor where the gap could be anywhere), and `floors` with matching `xMin`/`xMax` place gapped tiers only inside that shaft, alternating gap side so climbing forces a real (but short, since the shaft is narrow) zigzag — that's the general pattern for forced navigation, not a one-off hack. The base ground (`groundY`/`groundH`/`groundGaps`) stays a separate, special floor — it's the one `hasGapBetween`/pit-death care about — `floors`/`walls` are purely structural and don't carry that meaning.
- **Every zone caps its left and right edges with a `wall`** (thickness 40, full height) and insets `doors.left` by that same 40px so the door sits just behind the wall (mirroring how a `doors.right` naturally already sits ~40px before the true edge, with wall filling the gap behind it) — this is a level-design convention, not an engine requirement, but follow it for every new zone so world edges read as solid boundaries instead of the player just silently stopping at an invisible clamp (`player.x` is already hard-clamped to `[0, width-w]` regardless — the wall makes that boundary visible/physical, it doesn't change where the boundary is).
- **Wall gates (`zone.wallGates`, the enemies-must-die barrier) collide on X range only**, not a Y-bounded rect — `isGateBlocking(gate, rect)` checks `rect`'s X range against the gate's X, ignoring Y entirely (mirrors the trigger-zone "can't dodge by jumping" pattern, and for the same reason: picking a Y-span rect that's "tall enough" gets fragile the moment content moves vertically — this bit us once already, don't reintroduce a Y-bounded gate rect). `visualY`/`visualH` are separate, rendering-only fields — they don't affect collision. Since a gate's lock condition (`isGateLocked`) only ever scans `enemies[]`, anything that should *not* count toward "kill everyone to open the gate" (see `zone.ambientProps` below) simply needs to never be added to `enemies[]` in the first place — no exclusion list or flag needed.
- **Purely decorative background objects that must never be attackable, killable, or count toward a wall gate belong in `zone.ambientProps` (`{type,x,y,w,h}[]`), not `enemies[]`.** `draw()` renders them directly off `currentZone.ambientProps` (dispatching on `type`, e.g. `drawMimeBProp` for `"mimeB"`) with zero involvement from `damageEnemy`/`wallGates`/combat hit-detection — being absent from `enemies[]` is what makes "can't die" structural rather than a flag to remember and keep consistent everywhere. Only reach for this when something is meant to be scenery with an idle animation (a pulsing/rotating shape) and no interaction at all; if it should be attackable-but-unkillable, that's `enemy.hpFloor` on a real `enemies[]` entry instead (see zone 3's practice dummies).
- **`zone.name`** (a short human-readable label, e.g. `"1층 구역 3 - 근접 공격 연습"`) is a required field on every zone def going forward — the QA panel (below) and any future HUD zone-title display read it, falling back to the raw `id` if absent. Set it on every new zone file the same way `entryPoint`/`checkpoints` already are.
- **QA panel (`js/engine/qapanel.js`)** lets you warp to any registered `ZONES` entry instantly, grouped by floor, navigable by mouse click **or** W/S (move selection) + Space/Enter (confirm) — `qaPanelZoneIds`/`qaPanelSelectedIndex` track the flat (heading-free) selection order, kept in sync with the rendered `<button>`s by `renderQaPanelList()`. This is a real, permanent feature (not a throwaway dev hack) — the user's plan is to hand the same panel to players once they've fully cleared the game as a "zone select" reward, so it's built to the same standard as shipped UI: `warpToZone()` force-cleans any in-flight cutscene/fade/timestop state (mirroring what `endSequence()` does, since a warp can interrupt a sequence mid-flight and must not run that sequence's `onDone`), then delegates the actual zone entry to `enterZone()` (see the bullet above) — the same function the door trigger uses, so vitals/checkpoint behavior is guaranteed identical between the two paths by construction rather than by keeping two copies in sync by hand. While the panel is open, `loop()` (`js/main.js`) skips `update()` entirely (same mechanism as `timeStopTimer`) so the game doesn't keep running behind it, but still drains `justPressed` every frame — otherwise a key pressed while the panel was open would misfire as "just pressed" the instant the panel closes. `warpToZone()` is also written to be safe to call before any zone has ever loaded (`currentZone === null`) — this is what lets it double as the real bootstrap path (below). The panel itself no longer owns any `keydown` listener — see the pause menu bullet below for where Backquote/Escape/W/S/Space/Enter actually get routed. **Picking a zone (`pickZone(id)`) no longer warps immediately** — per user request it now opens the confirm dialog (see below) with the actual `warpToZone()`+cleanup wrapped in the dialog's `onConfirm` callback; canceling leaves the QA panel exactly as it was (nothing warped, nothing closed).
- **Main menu (`js/engine/mainmenu.js`) is the real bootstrap entry point**, not `main.js`'s tail. `main.js` no longer eagerly calls `loadZone`/`requestAnimationFrame` at parse time — instead it defines `gameStarted`/`ensureLoopStarted()`, and the loop only starts the first time something actually calls `ensureLoopStarted()` (which `warpToZone()` does at its end). Both menu buttons funnel through `warpToZone()`: "게임 시작" is just `warpToZone(BOOT_ZONE_ID)`; "구역 선택" opens the QA panel itself rather than building a second zone-list UI. The menu is never explicitly hidden when the QA panel opens over it — only `hideMainMenu()` (called once a zone is actually picked, or by the "게임 시작" handler) hides it — so canceling out of the panel (Escape/backtick) with no selection made naturally reveals the menu again with no dedicated "back" code path. Because nothing before the first `ensureLoopStarted()` call ever runs `loop()`, `draw()` never executes while `currentZone` is still `null`, so there's no null-check needed there for the pre-boot state. `mainMenuOpen` (mirroring `qaPanelOpen`'s pattern) tracks visibility for `loop()`'s freeze check and for the pause menu's routing decision (below) — it's *not* the same thing as `gameStarted` (which, once true, never goes false again): you can return to the main menu mid-session via the pause menu's "메인 화면" button, at which point `gameStarted` is still `true` but `mainMenuOpen` is `true` again. Both main-menu buttons are also keyboard-navigable (`mainMenuNav`, see the `createMenuNav` bullet below).
- **Pause menu (`js/engine/pausemenu.js`)** is what Backquote opens *during actual gameplay* (재개/메인 화면/구역 선택); at the main menu it still shortcuts straight to the QA panel like before, matching old behavior when there's nothing to "pause" yet. This file also owns the **one and only** `keydown` listener for Backquote/Escape/W/S/Space/Enter — it used to be split between `qapanel.js`'s own listener and nothing else, but once a second overlay (this pause menu) needed to react to the same keys with different meaning depending on what's currently showing, two independent listeners would race/conflict on the same keypress. The router checks, in order: confirm dialog open → handle its keys and stop (highest priority — it can appear over either of the overlays below); QA panel open → handle its keys and stop; pause menu open → Backquote/Escape closes it (identical to clicking "재개"); otherwise Backquote opens either the QA panel (if `mainMenuOpen`) or the pause menu. The pause menu relates to the QA panel exactly like the main menu does — opening "구역 선택" from it does *not* hide the pause menu, so backing out of the panel with no selection reveals the pause menu again, not a blank frozen game. **Any new full-screen overlay in this family must default to `display: none` in CSS** — `#pauseMenu` initially shipped with `display: flex` as its base rule (relying on JS to set `none`), which meant it covered and intercepted clicks on the main menu from the very first page load, before any code ever ran `closePauseMenu()`. Caught by an actual Playwright run, not by reading the code — worth re-testing new overlays in a real browser for exactly this reason. **"메인 화면" no longer acts immediately either** — same confirm-dialog wrapping as the QA panel's `pickZone` (below), per the same user request.
- **`createMenuNav(getButtons)` (`js/engine/menunav.js`)** is the shared W/S-move + Space/Enter-confirm helper behind the main menu and pause menu (`mainMenuNav`/`pauseMenuNav`) — generalizes the pattern the QA panel invented first (which still uses its own `moveQaPanelSelection`/`confirmQaPanelSelection`, since its list is dynamically rebuilt per-open with floor headings, unlike the other two menus' static button lists). Takes a `getButtons` function (not a fixed array) so it works for both static lists (just return the same array every time) and dynamic ones. Exposes `.move(delta)`/`.confirm()`/`.reset()` — `.reset()` must be called whenever the menu opens (sets focus back to index 0 and reapplies the `.menuBtnFocused` CSS class), not just once at load, or the focus highlight goes stale after the first use. Keydown routing for whichever menu is open still lives centrally in `pausemenu.js` (see above), not in this file.
- **Confirm dialog (`js/engine/confirmdialog.js`)** — a generic "예/아니오" modal used before hard-to-undo actions: warping to a zone from the QA panel, and returning to the main menu from the pause menu (both per explicit user request). `openConfirmDialog(message, onConfirm)` shows the message and stashes `onConfirm`; the underlying action only actually happens if "예" is chosen (click, or Space/Enter with the `createMenuNav`-driven default focus on "예" — deliberately *not* defaulting to "아니오", since this is a re-confirmation of something the user already deliberately selected, not a "did you mean to do this at all" guard). Follows the same "don't hide the screen underneath" convention as QA-panel-over-main-menu — canceling (아니오/Escape/backtick) just closes the dialog, leaving whatever opened it (QA panel, pause menu) exactly as it was. `z-index` (11) sits above the QA panel (10) since it needs to be able to appear on top of it. Routed with top priority in `pausemenu.js`'s central keydown listener (checked before QA panel/pause menu/main menu) since it can appear over any of them.

### Combat/movement (unchanged by the above — still exactly as it was pre-refactor)

- **`rectsOverlap()` (`js/engine/dom.js`) must keep its strict inequalities (`<`/`>`), never `<=`/`>=`.** It looks like an off-by-one that should be "fixed" to inclusive (a player resting exactly on a floor, per the `standingTopY` convention, is touching-not-overlapping for exactly one frame on entry) — it was tried, and it broke something unrelated and far worse: the X-axis wall-collision loop in `updatePlayer` relies on that same strict exclusivity to *not* treat "standing still on top of the ground" as "walked into the ground's side," since the ground segment is in the same `solidPlatforms` list checked for both axes. Switching to inclusive made every zone's ground register as a wall the instant the player stood on it, teleporting them to `x ≈ 0`. Only caught by actually walking a character around in a real browser — reasoning about the code predicted the opposite. If the "touching should count as overlapping" edge case ever needs solving again, solve it at the call site (e.g. force `onGround`/velocity explicitly, as `resetPlayerVitals()` now does on zone entry) rather than the shared comparison.
- **All tuning values live in one `CONFIG` object** (`js/config.js`), grouped by system with inline comments explaining units and relationships. Prefer changing `CONFIG` numbers over touching logic when adjusting balance. Where one value must stay derived from another (e.g. drift cooldowns must exceed invincibility + grace period), that relationship is implemented as a function (`getDriftCooldownOnCounter()`/`getDriftCooldownOnWhiff()`), not a second hardcoded constant — follow that pattern rather than reintroducing magic numbers that can drift out of sync.
- **Three interlocking combat systems** are the heart of the game and worth understanding before touching combat code:
  1. **Damage grace period** (`anchor` state) — hits don't apply to HP immediately; they sit in `player.pendingDamage` for `DRIFT_DAMAGE_GRACE_PERIOD` and only confirm if the player doesn't react.
  2. **Drift** (`drift` state, right-click) — a risk/reward parry-riposte: damage taken while drifting accumulates instead of applying, and resolves into a wide counterattack (or self-damage if nothing was absorbed) when the drift timer ends.
  3. **Hitstop/timestop** — `timeStopTimer > 0` makes the main loop skip `update()` entirely for a few frames on confirmed damage or a counter hit. `triggerTimeStop(duration, reason, onComplete)` supports chaining freeze segments (used for the drift counter's two-hit projectile-absorb bonus) — if you add a new hitstop trigger, reuse this rather than a parallel freeze mechanism.
  - Escape hatch: a projectile with `unblockable: true` (currently only the sniper enemy's shots) skips all three — `damagePlayer()` is never called for it, it goes straight to `applyDamageToHp()`, and the drift-counter's projectile-absorb loop explicitly skips it. It still respects `invincibleTimer`. If you add another must-dodge hazard, reuse this flag rather than inventing a parallel bypass.
- **Chaser enemy AI** deliberately perceives the player through a periodic poll (`CHASER_PERCEPTION_INTERVAL`), not live position, to feel laggy — but the actual attack-hit check always uses the real current player position/hitbox, never the perceived one. Keep that split when touching chaser logic: perception can lag, hit resolution must stay fair.
- **Every enemy carries generic detection/leash/attack-range instance fields** (`detectionRangeW/H`, `leashRangeW/H`, `attackRangeW/H`, seeded from `CONFIG` in each `make*` factory) plus an aggro concept — turret/sniper have an explicit `enemy.aggro` boolean toggled in `updateTurretAI`, chaser's equivalent is derived from `aiState` (patrol/return = not aggroed). An enemy only acts (fires/telegraphs/chases) once aggroed; before that it's rendered but inert — that inert state is where per-type idle animations are meant to go later, so don't collapse it back into "act immediately once `hasBeenVisible`." Turret/sniper's `detectionRangeW/H` default to a fixed `ENEMY_DEFAULT_DETECTION_RANGE_W/H` (pinned to the *original* 960×540 screen size, not the live `W`/`H`) — that pin is deliberate: the camera viewport (`W`/`H`, canvas `width`/`height`) is now wider than that so the player can see an enemy on screen before it's actually in range. Don't derive the default range from `W`/`H` or this collapses back to "visible = aggroed."
  - `leashRangeW/H`/`attackRangeW/H` are the general on/off switch for "does this enemy ever give up aggro": a finite number behaves like chaser's leash (`dist > range` can go true again later), `Infinity` makes that comparison permanently false — turret/sniper use `Infinity` for both, so once `aggro` flips true from the one-time detection check it never flips back. No separate "infinite" flag or sentinel needed; it's just what `Infinity` already does in a `>` comparison. Reach for this when adding a new enemy that should either have a real leash (give it a number) or aggro forever once triggered (give it `Infinity`).
- **Enemy HP is in half-point increments** (ground attack = 1, air attack = 0.5 via `getAirAttackDamage()`), rendered as diamond pips (`drawHpPip`) that can show a half-fill. Don't inflate monster max-HP to dodge fractional damage — it was tried once and diluted the drift counter's relative punch (its multiplier scales off damage the player took, not off monster HP).
- **Air attack always overwrites `player.vy`** to `-AIR_ATTACK_HOP_FORCE` on trigger (see `startAttack`/the attack-input block in `updatePlayer`), independent of `jumpsUsed` — this is what lets jump → double jump → air attack chain into a de facto triple jump. Don't gate it behind `MAX_JUMPS`. It's gated by its own counter instead: `player.airAttacksUsed` vs `CONFIG.MAX_AIR_ATTACKS` (1), reset to 0 alongside `jumpsUsed` at every landing spot — without this, the attack's recovery is short enough that spamming it while airborne never lets you touch the ground. When out of charges, the attack input is silently ignored while airborne (same as pressing jump with no jumps left) — no swing, no hitbox, no hop.
- **Rendering** happens in world space inside a single `ctx.translate(-camera.x, -camera.y)` block in `draw()` (`js/rendering.js`); HUD elements, the cutscene textbox (`#cutsceneBox`), and the fade overlay (`#fadeOverlay`) are DOM overlays outside the canvas and are camera-independent. The fade overlay in particular must stay DOM (not a canvas fill) so it also covers the HP bar — a "black screen" that leaves the HUD visible isn't actually a fade.
- **Input** unifies keyboard and mouse buttons through one pipeline (`heldKeys`/`justPressed`/`pendingKeyAfterFreeze`, `js/engine/input.js`) so mouse clicks get the same during-hitstop input-queueing treatment as keys.
- The ghost NPC companion is purely cosmetic and intentionally has zero references from any collision/damage function — don't wire it into gameplay logic. It became the `gyeol` AI companion starting in `f2z1_gyeol_encounter` (2층 구역 1) — she is confirmed to **never** participate in combat, permanently, per explicit user decision (not just "for now"); this invariant is not up for revisiting. `updateGhostNpc()` (`js/entities/player.js`) does give her one *visual-only* awareness of the world despite this: `isGhostSideBlocked(side)` checks whether her computed follow-offset position would overlap `currentZone.solidPlatforms` (including zone-boundary walls), and flips her to the other side of the player if so — without this, standing flush against a wall while facing away from it put her target position inside the wall, visibly clipping through it (reported by the user). This is a pure "don't pick an overlapping spot" correction, not a real collision response, so it doesn't contradict the no-gameplay-interaction invariant above.

## Git / deployment

- Repo is linked to Vercel (`.vercel/project.json`) and to GitHub (`origin`). Commits to `master` do not auto-deploy; deploying is a separate explicit step (`vercel` / `vercel --prod`).
- **Committing is pre-authorized and automatic**: after finishing a meaningful chunk of work (a feature, a fix, a session's worth of changes), commit it without waiting to be asked — the user wants work saved as it happens, not batched up for an explicit "commit this" request. Use judgment on commit granularity (don't commit mid-edit or in a broken state); split unrelated work into separate commits rather than one giant one.
- **Pushing to GitHub (`origin`) is pre-authorized**: after committing, push to `master` automatically without asking for confirmation first.
- **Vercel deployment stays manual**: never run `vercel` / `vercel --prod` unless the user explicitly asks for that deploy, even after pushing to GitHub.
- No CI, no PR checks — the only verification available is manual play-testing and reasoning about the code (or writing a throwaway Node script that copies the relevant pure-logic functions to simulate them, since the real code depends on `<canvas>`/DOM).
